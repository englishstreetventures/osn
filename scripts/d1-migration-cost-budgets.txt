# D1 migration-cost budgets — read by scripts/guard-d1-migration-cost.ts, and
# by nothing else. This file, not the script and not a workflow step, is where
# the number lives.
#
#   <migrations-dir>  <budget, in estimated D1 rows written to replay it from zero>
#
# The guard replays the chain into an in-memory SQLite and counts schema
# writes, which is exact. It then PRICES them at 27 D1 rows each, which is not:
# the evidence puts that constant somewhere around 22 to 27, and the script's
# own header carries both anchors and why the band is that wide. So read the
# row figures here as indicative, and pessimistic by up to about a fifth rather
# than optimistic. The guard also prints the same line in schema writes, which
# is the form to trust.
#
# RE-BASELINING. Run `bun run scripts/guard-d1-migration-cost.ts --all`, read
# the printed cost, and edit the row here. Two rules, from
# wiki/conventions/bundle-size-guards.md:
# a budget is a number somebody chose, with the reason in the commit; and a
# guard that only ever gets raised is not a guard. This one has a remedy the
# bundle guard does not — squashing the chain into a fresh baseline puts the
# cost back down instead of moving the line up. Reach for that first.

# The line is 200 schema writes, 5400 rows priced at 27. The squashed
# baseline (2026-11-19) is 150 schema writes, one CREATE per table, index and
# trigger, 4050 rows; the line sits 50 writes above it. The mistake this guard
# exists to catch is not one bad migration — nothing in a chain that goes over
# the ceiling is wrong on its own — it is the chain regrowing until a day's
# rebuilds no longer fit.
#
# The line is not twice the baseline: the schema itself is 150 objects, so
# twice the baseline would raise the line, and a guard that only ever gets
# raised is not a guard. The owner chose to keep 200 (2026-11-19,
# englishstreetventures/osn#2096). A squash needs no production step
# (cire/db/README.md), so tripping sooner costs one more squash, not a raise.
#
# In rows: 4050 for the baseline, 5400 at the line, so a replay goes from 4%
# to 5.4% of the day's 100,000 rows written and from roughly 24 replays a day
# to 18. Those row figures move with the constant; the 150-against-200 does not.
#
# The headroom is 50 schema writes: four to eight ordinary migrations
# (`gifts_keep_their_account` is 6, `platform_refunds` 2, and the heaviest of
# 0058-0081, 0058_gift_summary_and_stripe_state, 12). When the chain reaches
# the line, squash it into a fresh baseline again (cire/db/README.md has the
# method) rather than raise the line.
cire/db/migrations 5400
