# Status + Up Next

The single high-churn shard. Update **Current Status** when a major slice lands; tick / append to **Up Next** as priorities shift. All other tracking lives in sibling shards under `wiki/todo/`.

## Current Status

Monorepo built and functional. `cire/db` models families with a shareable `publicId` (e.g. `PATEL-JOY-RK97`) and per-family guests; `cire/api` exposes `POST /api/claim` (publicId-only lookup, mints a session), `POST /api/rsvp` (session-cookie gated, per-person per-event with dietary), `GET /api/organiser/guests`, plus rate-limit middleware on `/api/claim`. Organiser portal split into its own Astro app (`cire/organiser`) with `GuestTable` consuming the new shape. **PR-A** landed events metadata + `imports` table + `guests.externalId`. **PR-B** landed session-cookie auth: a 256-bit `cire_session` token is minted on successful claim and set as `HttpOnly; SameSite=Lax; Path=/` (no `Domain=` — host-scoped); `/api/rsvp` is behind a `sessionAuth` middleware that derives `familyId` from the session, dropping `familyPublicId` from the body; CORS now echoes the configured origin with `credentials: true`. **PR-C** is now in: hand-rolled RFC 4180 CSV parser with formula-injection guards, an Effect-based diff service that reconciles parsed sheets against the live DB (creates / updates / removes per family + per guest + per event-link, plus state-loss warnings for guests with non-default RSVPs), R2-versioned uploads keyed at `imports/<importId>/{events,guests}.csv`, and a `revertImport` path that re-applies a previous snapshot. Routes under `/api/organiser/import/{preview,apply,revert,list}` are gated behind a shared-secret `X-Organiser-Token` header (an interim measure, since deleted — see the OSN-merge paragraph below). Backend is Effect-based with Effect Schema validation; tests co-located `*.test.ts` under `bun test` (132 api, 148 web). Migrations: `0001_initial.sql`, `0002_add_rsvp_dietary.sql`, `0003_events_metadata_and_imports.sql`, `0004_perf_indices.sql`. **PR #28** swaps the fixture mehndi/sangeet/wedding/reception set for the real five-event programme (Catholic 31 Oct → Kitchen Tea 20 Nov → Mehendi 22 Nov → Hindu 25 Nov → Reception 28 Nov), wires real Pinterest moodboards on each, invites the default demo code `PATEL-JOY-RK97` to all events, and reworks `PinterestBoard` from `<iframe>` to the documented script-widget pattern with a "View moodboard on Pinterest" fallback for tracker-blocker users (see [[deferred]] resolved row).

**OSN merge (2026-06):** cire.git was imported into the OSN monorepo as the `cire/` workspace via git subtree — packages are now `cire/web` (:4321), `cire/organiser` (:4322), `cire/api` (:8787), `cire/db` (the old `apps/*` / `packages/*` nesting is gone). Organiser auth is real: the portal signs in with **OSN passkeys** (`@osn/client` + `@osn/ui`), `cire/api` verifies the issued ES256 access JWT (`aud: "osn-access"`) via `osnAuth()` from the new `@shared/osn-auth-client` package, and `weddingOwner()` / `ownedWedding()` enforce ownership against the new multi-tenant scaffold (`weddings` root table; `families`/`events`/`imports` carry `wedding_id` NOT NULL FK; migration `0006_multi_tenant.sql`). The interim `X-Organiser-Token` shared secret is **deleted**. Cire also adopted `@shared/typescript-config` + `@shared/rate-limit`, and `bun run dev:cire` (repo root) runs the full stack incl. `@osn/api`. A 12-probe headless E2E against the live dev stack passed. See `[[wiki/apps/cire]]` + `[[wiki/systems/cire-auth]]` in the root OSN wiki. The runtime D1 layer is wired. **The bootstrap-owner mechanism is now removed (`feat/cire-organiser-open-access`):** any authenticated OSN user is a first-class organiser — no `BOOTSTRAP_OWNER_PROFILE_ID`, no seeded owner, no boot gate; migration `0015_drop_bootstrap_wedding.sql` deletes the orphaned `wed_bootstrap` demo row. **Prod wrangler config is now wired (PR #121):** the real D1 `database_id` `6e835474-e0a7-4db9-8883-3247c3c891cd` is set, the organiser portal origin is added to the prod `WEB_ORIGIN` allowlist (placeholder domain pending), the OSN issuer/JWKS URLs are flagged required-before-prod, and D1 + R2 bindings are redeclared under `[env.production]` (named envs don't inherit top-level bindings). **A GitHub Actions deploy pipeline (`.github/workflows/deploy.yml`, PR #128)** gates on build/test, applies remote cire D1 migrations, then deploys the cire-api Worker + cire-web Pages — see the root `[[wiki/runbooks/production-deploy]]`. The remaining pre-prod step is confirming the real prod domains in the URL placeholders (no bootstrap-owner secret is needed anymore). **Co-host content access:** co-hosts (`wedding_hosts`) now get the **full** wedding-content surface, not just the dashboard reads — the spreadsheet import (`/import/*`) and the invite-builder customisation routes moved from `weddingOwner()` to `weddingMember()`, and `OrganiserApp.tsx` no longer hides `<ImportPanel>` from them. Owner-only stays drawn at *managing the wedding itself*: re-minting/regenerating codes, adding/removing co-hosts, and deleting the wedding. See the capability matrix in `[[wiki/systems/cire-auth]]` (root). **RSVP CSV export (`feat/rsvp-csv-export`):** `GET /api/organiser/weddings/:weddingId/rsvps.csv` (gated by `weddingMember()`, so owner or co-host) downloads one row per guest — Family Code, Family Name, Guest First/Last Name, one column per event (`Attending`/`Not attending`/`Maybe`/`No response`, blank = not invited), then Dietary Requirements; **non-RSVP'd guests are included**, host families excluded, rows sorted by Family Code. Built + formula-sanitised server-side (`services/rsvp-export.ts`); a "Download RSVPs (CSV)" button in `GuestTable.tsx` triggers the blob download via the extracted shared `lib/download.ts` helper. See `[[api]]`. **Guest-list search (2026-08-07):** `GuestTable.tsx`'s read-only Households/RSVPs list gained a search box that filters the already-loaded roster client-side by household name, member name (word-prefix, via `@shared/db-utils/search`'s shared `tokeniseQuery`/`tokensPrefixName` — the root OSN wiki's `[[wiki/systems/social-graph]]` §Search convention), or family-code substring — no new endpoint, since the whole roster is already fetched per wedding. Debounced 200ms (a plan can hold up to 1000 guests) and keeps a matched household's row identity stable across keystrokes (member-visibility is a per-row memo, not a rebuilt array) so `<For>` reuses unaffected rows instead of remounting them.
