The `musubi-passkey` flow adds an authenticator app in the Security section of Settings and removes it again, each behind a passkey step-up, with the code computed from the setup key the page shows (`totpCode` in the fixtures, on the suite clock). It then moves the page's clock past the access token's expiry and opens Security: one `/token` grant renews the token before any of the three authenticated reads leaves the page, and none is refused. It lists the connected apps and sees the empty state. Then it drops the session cookie and does it again: the refused grant is sent once, no read goes out, and the page shows the signed-out Settings note with the stored account gone.

The stack now builds Musubi and serves the build through Wrangler's local asset server, which applies its `_headers` as the deployed Worker does, so every Musubi page in the flows runs under the Content-Security-Policy that ships. The build carries Turnstile's always-pass test sitekey, and the fixtures stand in for Turnstile at its real script and frame URLs. The fixtures collect every Content-Security-Policy message a page logs, and each Musubi flow checks that no Musubi page logged one. `musubi-passkey` checks the policy it is served; that no stored value holds a token once signed in and once renewed; that a reload keeping storage is signed in by one grant; that a reload with the stored account and no cookie is signed out by one refused grant and forgets the account; and it ends by signing in to Pulse through Musubi's `/authorize`, which loads Turnstile and the consent screen.
