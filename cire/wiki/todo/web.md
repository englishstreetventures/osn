- [x] **The whole invite swept onto the prose gold** (`claude/rsvp-notice-contrast-fix-m5px1l`, 2026-08-01) — the follow-up to the RSVP-by fix below, and the reason a rescan of a pale invite now comes back clean rather than reporting the eyebrow beside the line that was fixed. 45 utility sites across 15 components plus 8 raw-CSS declarations (`SiteFooter.astro`, `LegalLayout.astro`) move `text-gold` → `text-gold-ink`. The rule: **gilt paints borders, fills, icons and large display text; gold-ink paints anything read below WCAG's large-text bar** — measured against the SMALLEST size each element can render at, which is the `clamp()` minimum times the organiser's `small` heading scale (0.85). That is what separates gala's claim `h2` (20.4px at `small` → gold-ink) from classic's (27.2px → metal). Five deliberate keeps: both packs' hero couple names, classic's claim heading, the 404 numeral, and `MapPreview`'s pin (an icon, not text). The consent "Always on" chip also loses its `/80` alpha — an alpha over a surface has no single ratio, so `text-gold-ink/80` would have looked fixed without being fixed. Guarded by `styles/gold-text-token.test.ts`: a static source scan with a five-entry allow-list, each with a written reason, rather than a size heuristic — parsing `calc(clamp(…)*var(…))` to guess at 24px is how a guard fails open. **The branch's own pre-PR review then found three defects in this commit, all fixed on branch.** (1) The sweep was a regex over whole files, so it rewrote the RATIONALE COMMENTS too — three of them read "`text-gold-ink`, not `text-gold-ink`", i.e. the only in-source statement of the invariant asserted nothing. The guard *forced* it: matching whole file contents, it could not tell a class from a mention of one, so an intact comment would have failed the test. Comments are stripped before matching now, and the three are restored. (2) The guard compared only the SET of offending files, so three allow-listed files that also hold swept sites could have had one reverted silently — it compares per-file COUNTS now. (3) **C-L5**: the hero tagline's `text-gold-dim` measures **2.05:1** on `evergreen` (the alpha is unenforceable — `contrastOklch` ignores alpha), worse than anything this branch set out to fix, and I had deferred it on the false premise that its backdrop is always a photo — the hero image is optional, and without it the backdrop is derived tokens. Both taglines moved to `text-gold-ink`; the guard now treats `-dim` as the metal and catches `text-gold/80` forms. All four regression shapes verified to fail the guard. 650 → 654 tests. - [x] **Invite styling pass: centred RSVP-by line, bigger desktop type, contrast warnings back, hex field fixed** (`claude/cire-invite-styling-picker-87ni7b`, 2026-08-01) — four asks in one. The bloom pair was dropped outright: `--color-bloom` has no render site anywhere in `cire/web`, so it warned about a colour no guest can see. All five presets are clean, which is what makes a non-empty list worth reading; it warns rather than blocks, since the fix is the organiser's design call. (4) **The hex field's involuntary autocomplete is fixed at the root.** Guarding our own commit path was never enough: Kobalte's `ColorField` runs its own blur handler that parses the field and writes the expansion back, and because Kobalte composes handlers with `composeEventHandlers` — every handler called unconditionally, `preventDefault` ignored — it could not be pre-empted from outside. Three digits into `#d4af37`, `#d4a` became `#DD44AA` the moment focus left the field (clicking the area, the next picker, anywhere outside the popover). The field is now a plain `<input>` we own: `onHexBlur` re-prints a committed hex in canonical form and restores the last committed colour for anything incomplete, so leaving a half-typed entry never invents a colour. 3-digit shorthand no longer expands — the deliberate trade, since every full hex passes through its own three-digit prefix on the way in. A non-hex keystroke is refused and the DOM value pushed back by hand (a controlled Solid input re-renders nothing when the signal is unchanged). **Pre-merge reviews found five more, all fixed on branch and each pinned by a test verified to fail with its fix disabled**: the wrong-surface bug above (**C-M1**), a live region that re-announced the whole block on every pointermove (**C-L1** — region now permanently mounted with conditional contents, ratios `aria-hidden`, memo carries an `equals` comparator), "needs 3:1" printed beside a text pair (**C-L2**), a hex discard with no programmatic notification (**C-L3** — now `aria-invalid` + a described-by "Needs 6 digits — kept #D4AF37"), and `<For>` over freshly-allocated objects tearing down every warning row per drag frame (**P-W1**, now `<Index>`).   - **A household with no guests was invisible and got deleted.** `buildDraft` reconstructed households from the flat guest rows, so a household added-but-not-yet-filled (or emptied by an earlier save) wasn't in the draft — and since the draft is the whole truth, absence is deletion. "Add household → Save" therefore minted a claim code for a household that then vanished from the editor and was silently deleted by the next save. Both editors now load `GET .../households` through a new `lib/households-store.ts` and carry guest-less households as empty cards ("No guests in this household yet") that can be filled in or deleted on purpose.
  - **Discard didn't always discard.** `discard()` rewound to `undoStack[0]`, but the stack is capped at 100 and every keystroke checkpoints — past that the oldest entry is a mid-edit state, so a long session's Discard kept edits *and* reported the draft clean. The store now snapshots the loaded state at `load()`/`commit()` and restores that.
  - **No unsaved-changes guard.** Neither editor registered `lib/unsaved-guard.ts` (the invite builder has since it shipped), so a stray module/tab click threw the entire draft away with no prompt. Both now register it while mounted, plus a `beforeunload` listener while dirty.
  Also: an apply error rendered only in the sticky bar, which sits *behind* the preview modal's overlay — a failed apply looked like nothing happened; the error now renders in the dialog too, and a 409 dismisses the stale preview rather than leaving a modal whose only button can 409 again. all three caches now carry a per-wedding GENERATION that an invalidation bumps, so a fetch already in flight discards its rows instead of caching them — dropping the cache entry alone was not enough, since the fetch's own `.then` simply wrote pre-mutation rows into a fresh entry (caught by the store test the review asked for, T-U1). `ImportPanel` and `ChangeHistory` invalidate households alongside events + guests (S-L5): the three are one consistency unit now, and invalidating two of them is this branch's bug one level up. organiser 663 → 687.
- [x] **Schedule re-order is drag-and-drop** (`claude/event-reordering-drag-drop-31byc6`) — the host dashboard's Schedule → Edit list dropped its per-row ▲/▼ buttons for a grip handle you drag, using [solid-dnd](https://github.com/thisbeyond/solid-dnd) (`DragDropProvider` + `DragDropSensors` + `SortableProvider` + `createSortable`, `closestCenter`). Native SolidJS, so there's **no adapter layer** — the row registers via `sortable.ref` and applies `maybeTransformStyle(sortable.transform)` itself, with `sortable.dragActivators` spread onto the grip; deliberately not the `use:sortable` directive, which would make the whole row draggable and swallow text selection plus the row's Edit/Delete buttons. Draft-store API followed: `moveEvent(key, ±1)` → `reorderEvents(from, to)`. **solid-dnd has no keyboard sensor and makes no announcements**, so dragging alone would have made this an accessibility regression on the arrows it replaced — the list owns that path itself: the grip is a real `<button>` handling Arrow Up/Down, auto-repeat ignored so one press is one move, focus re-focused explicitly after a move (a keyed `<For>` moves the node, but a DOM move is remove-then-insert and focus doesn't reliably survive it), and every move announced via a polite `role="status"` live region that clears before it sets so an identical consecutive move still speaks. The /prep-pr review then caught that this was **still** not enough: NVDA/JAWS browse mode eats unmodified arrow keys for its own virtual cursor, so screen-reader users would read the hint, press the arrows and get nothing — a WCAG 2.1.1 regression against the Enter/Space-activated ▲/▼ pair. Each row now also carries `sr-only` (`focus:not-sr-only`, edge-`disabled`) "Move X up/down" buttons on the same handler; the **visible** arrows stay gone. Measured main-chunk cost +13.1 KiB raw / +4.3 KiB gzip, so no code-split needed (~23 KiB headroom left under Vite's warning). **Library choice**: [neodrag](https://github.com/PuruVJ/neodrag) was ruled out on capability, not maintenance — it's a free-positioning draggable with no droppables or collision detection, so sortable lists would mean hand-writing the hit-testing; dnd-kit works but is React-adapter-only (we'd own a Solid adapter) and at ~105 kB forced a `lazy()` split. **Accepted risk**: solid-dnd's last release is Nov 2023, nearly three years stale — mitigated by it being small, zero-runtime-dep, pure DOM+geometry, and by tests that drive a REAL synthetic pointer drag end-to-end (sensor → collision → commit, with `getBoundingClientRect` stubbed since happy-dom does no layout), so a Solid upgrade that breaks it fails loudly. **Wants a real-browser eyeball** — drag feel, the shift/settle animation and the grip's hover/focus styling are beyond happy-dom. See `[[architecture/drag-and-drop]]` and `[[architecture/guest-event-editor]]` (E7).
- [x] **Guest saw NO events after a successful claim — Motion One → v12 API drift in the unlock reveal** (`fix/invite-events-reveal`) — prod bug (claim `NGUYEN-KOI-AYXVP4`): claim succeeded, welcome banner rendered, all event cards were in the DOM, but the events `<section>` sat at its base `opacity-0` class forever. Root cause: `UnlockReveal.motion.ts` was written against Motion One (v10) semantics but the repo has shipped `motion` v12 since the animation landed — v12 silently ignores the removed `easing` option AND does not persist a keyframe animation's final value, so the section animated 0→1 then reverted to the `opacity-0` base. Fix: each reveal step now writes its end state as an inline style (keyframes only paint the transition), `easing`→`ease` + stagger `{start}`→`{startDelay}` across `UnlockReveal.motion.ts`/`Modal.motion.ts`, every animate call guarded (throw or stalled `finished` can no longer hide the invite; 1s cap per step), and `InvitePage.handleClaimed` force-reveals on a failed motion-chunk import. Drive-bys: escaped the code input's `pattern` hyphen (Chrome v-flag rejected the whole pattern), and `deploy.yml` now bakes `PUBLIC_OSN_ISSUER_URL` into the guest-site build (bundle was dialling `http://localhost:4000` for the Pulse account-link island in prod).
