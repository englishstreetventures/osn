An owner can download a whole wedding as one ZIP: `POST /api/organiser/weddings/:weddingId/archive`, owner only, a deleted wedding answering 404, never locked by tier, ten a day per owner before the shared export limit, which it also spends. It holds every CSV the portal offers, new ones for households, vendors, the gift list, every seating plan, the wedding's settings and the invitation's words and questions, the schedule and guest list as the import reads them, and the pictures and uploaded spreadsheets the wedding holds in R2, up to 900 files and 256 MiB of them; `manifest.json` names any file a limit kept out, any that could not be read, and any CSV its row ceiling cut. Every database read finishes before the first byte, so a failed one is a 500; entries are stored with a native CRC-32 (`fflate`, `node:zlib`). cire-api also answers osn-api's account-export call, `POST /internal/account-export` (scope `account:export`): one `cire.weddings` line per seat the account's profiles hold, with the role, who gave the seat, how many other owners the wedding has, and for an owner of a live wedding the host-portal page that downloads it. New counters `cire.wedding.archive.downloads`, `cire.wedding.archive.files` and `cire.account_export.requests`.

The host portal gains Settings › Export (`#/w/<weddingId>/settings/export`): an owner presses "Download wedding", sees how much has arrived while the archive streams, and gets the ZIP saved as `cire-wedding-<slug>.zip` only when it ends in the ZIP's end record, so an archive cut short is reported and never saved; a refusal, the download limit included, says what to do and is never retried for them. Anyone else who opens the address is told only an owner can download it and to ask one, and the delete-wedding dialog now links the page for a copy first.
