### cire/wiki/todo/security.md — Invite styling + contrast warnings + hex picker (claude/cire-invite-styling-picker-87ni7b, 2026-08-01)

- [x] **C-M1** (fixed on branch) — **the residual-contrast warnings measured the wrong surfaces, so they could stay silent on the copy guests actually read.** `RESIDUAL_PAIRS` measured `--color-surface` under messages naming "event cards", and `--color-surface-raised` under a message naming "pop-ups". It is the other way round on the guest site: `EventCard` is `bg-surface-raised` (as is the RSVP sheet's notice block), while `AnimatedModal` and the sheet's sticky footer are `bg-surface` — and everything on `bg-surface` is already enforced by `derivePalette`. Walking the full (ink, muted, gilt) × (ground, card, raised) matrix, `muted-on-raised` and `gilt-on-raised` were covered by neither enforcement nor warning, which is exactly where every event card lives. **Fixed on branch:** the table now measures the surface each message names, gains `muted-on-raised`, and drops the bloom pair entirely (`--color-bloom` has no render site anywhere in `cire/invites`, so it warned about a colour no guest can see). Pinned by a directional test that fails if the two surfaces are crossed again. See [[invite-builder]].
- [x] **C-L2** (fixed on branch) — **the warning told organisers that secondary text "needs 3:1".** `muted-on-ground` used `WCAG_UI_MIN` and printed it verbatim, but every `--color-text-muted` site on the invite is small text (0.74–0.92rem), which WCAG AA puts at 4.5:1 — so a palette at 3.2:1 cleared the check, printed no warning, and failed AA on the guest site. **Fixed on branch:** both muted pairs use `WCAG_TEXT_MIN`. All five curated presets clear 4.5 there (4.65 worst case), so it costs no false alarms.
- [x] **C-L3** (fixed on branch) — **an incomplete hex was discarded on blur with no programmatic notification.** Snapping the field back is visible to anyone watching it and invisible to everyone else, so a screen-reader user could leave the field believing their colour applied (WCAG 3.3.1). **Fixed on branch:** a discard sets `aria-invalid` and posts an `aria-describedby` line naming what was kept ("Needs 6 digits — kept #D4AF37"), cleared as soon as typing resumes.
- [x] **C-M2** (fixed 2026-08-01, `claude/rsvp-notice-contrast-fix-m5px1l`) — **fixed at the token level rather than by retuning the two presets, because the field report was a CUSTOM palette, not a preset.** A live invite's RSVP-by line measured 3.35:1 (axe / WCAG 1.4.3) — the same defect one DOM level up from the date: `--color-gold` is the metal, held to the 3:1 UI floor by design, and painting normal-size text with it is the bug. Darkening `chapel` and `garden` would have fixed neither. `@cire/theme` now derives **`--color-gold-ink`** — the organiser's own hue walked to `WCAG_TEXT_MIN` against `ground`, `card` AND `raised` (a section's tone is their pick, so any can be the backdrop) — while `--color-gold` stays exactly as chosen for rules, borders, buttons and display headings. The event-card date and the RSVP-by line in both packs use it; `gilt-on-raised` therefore keeps its 3:1 bar legitimately (nothing normal-size is painted in gilt on that surface any more) and the exception comment is gone. `--color-text-muted` moved to the same three-surface text minimum in the same pass — the field palette had it at 4.36:1 behind the _closed_ form of that line, and it is a derived grey nobody picks, so enforcing it costs no design fidelity. Pinned by preset sweeps over both prose tokens, a regression test reproducing the 3.35:1 palette, and per-pack class assertions. See [[invite-builder]], [[rsvp-deadline]]. Related: **C-M3** below.
- [x] **C-M3** (fixed 2026-08-01, `claude/rsvp-notice-contrast-fix-m5px1l`) — **the rest of the invite swept onto `--color-gold-ink`.** 45 utility sites across 15 components plus 8 raw-CSS declarations in `SiteFooter.astro` and `LegalLayout.astro`: section eyebrows, control labels (`Add host`, `Respond`, `Add to Calendar`, the Pinterest and map links), modal headings, the consent banner/gate/preferences links, the claim-code notices. The rule applied was **gilt paints borders, fills, icons and large display text; gold-ink paints anything read below the WCAG large-text bar** — and the bar was computed against the SMALLEST size each element can render at, i.e. the `clamp()` minimum times the organiser's `small` heading scale (0.85), not the value read off the class. That distinction decided two cases: gala's claim-section `h2` (`clamp(1.5rem,4vw,2rem)` → 20.4px at `small`) moved to gold-ink, while classic's (`clamp(2rem,5vw,3rem)` → 27.2px) stayed the metal. Five sites keep `text-gold` deliberately — both packs' hero couple names, classic's claim heading, the 404 numeral (all large text) and `MapPreview`'s pin (an SVG icon, a graphical object at the 3:1 bar). `ConsentPreferences`' "Always on" chip lost its `/80` alpha along with the swap: an alpha-modified colour over a surface has no single ratio to enforce, so `text-gold-ink/80` would have looked fixed without being fixed. Pinned by `cire/invites/src/styles/gold-text-token.test.ts`, a static source scan whose allow-list is an explicit five-entry list with a stated reason each — deliberately not a size heuristic, since parsing a `calc(clamp(…)*var(…))` to guess whether it clears 24px is the kind of cleverness that fails open. Verified to FAIL when a single `text-gold-ink` is reverted. web 650 → 653. Still open: **C-L5** below.
- [x] **C-L5** (filed then FIXED on the same branch, 2026-08-01) — **`text-gold-dim` painted the hero tagline at 2.05:1, and the first cut of the guard was written never to see it.** Both packs set the couple's subtitle in `--color-gold-dim` at 0.8rem uppercase — normal-size text. That token is the metal at 0.35 alpha and **nothing checks it**: `contrastOklch` ignores alpha by design, because a translucent colour over an unknown backdrop has no single ratio. Composited it measures **2.05:1 on `evergreen`**, the scheme where the undimmed metal clears 8:1 — below even the 3:1 UI floor, and worse than the 3.58:1 that got C-M2 filed. **I deferred this on a premise that was wrong**: "the backdrop is an organiser-uploaded photo, so no palette-level fix reaches it". The hero image is OPTIONAL (`<Show>`-guarded), and with no image the backdrop is the scrim over `--invite-hero-grad-*` — all derived tokens, which a palette-level fix reaches directly. **Fixed:** both taglines moved to `text-gold-ink`. Over a photo it is still strictly better, and the scrim tracks the page's own lightness (dark scheme → dark scrim, light → light), which is the direction this token needs. The guard's exemption is gone too — it now treats `text-gold-dim` AS the metal and catches opacity-modified forms (`text-gold/80`), both verified to fail. Caught by the branch's own pre-PR review, not in production.

### cire/wiki/todo/security.md — Invite builder mobile section menu — review findings (claude/mobile-invite-builder-submenu-017xyv, 2026-07-30)

- [x] **SM-C-M1** (fixed on branch) — **the open menu obscured the element focus landed in.** The menu is an opaque overlay (`absolute … bg-bg … shadow-lg`) across the top of the active section, and nothing closed it when focus left: the dismiss paths were Escape (bound to the tabs and the trigger), a selection, and an outside `pointerdown`. A keyboard user who tabbed forward instead of selecting went trigger → active tab → "Preview" → **the first form control of the active section**, hidden behind the still-open menu — and Escape is not bound to that field, so there was no keyboard way to uncover it. WCAG 2.2 SC 2.4.11 _Focus Not Obscured (Minimum)_, AA; the criterion's "reveal without advancing focus" exception does not apply. Kept at Medium rather than the Low that the WCAG-2.2-vs-EN-301-549-v3.2.1 version gap would argue for (cf. **DND-C-L2**), because the failure mode is loss of function — editing an invisible field — not a measurement nitpick. **Fixed on branch:** `onFocusOut` on the `<nav>` closes when `relatedTarget` is outside it; focus moving within the nav (tab→tab, or the close's own restore to the trigger) does not dismiss.
- [x] **SM-C-L1** (fixed on branch) — the new `ArrowDown`/`ArrowUp` cases ran at **every** container width, including `@3xl/builder` and up where the tablist is the static single-line row, and the handler's `preventDefault()` then suppressed page scroll from a focused tab. Confirmed regression against `origin/main`, which had no vertical handling; APG reserves Down/Up for `aria-orientation="vertical"` tablists precisely so a horizontal one doesn't capture them — the same APG-conformance surface a previous cut of this nav had pinned as **C-M1**. **Fixed on branch:** both cases gated on `sectionMenuOpen()`.
- [x] **SM-C-L2** (fixed on branch) — in the open menu's row-major two-column grid, `ArrowDown` stepped `+1`, landing on the item to the **right** rather than the one below, and the test asserted that mapping, so CI defended the wrong spatial model. **Fixed on branch:** the vertical pair steps by `SECTION_MENU_COLUMNS`. Two columns kept rather than going single-column (the review's alternative): 8 rows is ≈396px, which overflows the `max-h-[60vh]` cap on a landscape phone and re-introduces the scrolling this branch exists to remove. The column count is a CSS fact the handler cannot read back, and Tailwind only emits utilities it finds as **literal source text** — so the class stays literal and an exported constant plus a static drift guard in the tests keeps the pair honest (same treatment as the `auto-grid` / `page-frame` utilities).
- [x] **SM-C-L3** (fixed on branch) — the trigger's Shown/Hidden dot is `aria-hidden` and its `aria-label` omitted the state; because `aria-label` overrides subtree content, the `sr-only` technique the tabs use would have been dropped too. So the collapsed trigger conveyed three things to a sighted organiser and two to a screen-reader one, against a design whose stated claim is that it can be read instead of opened. **Fixed on branch:** the state is a clause in the label, in `SegmentBadge`'s wording.
