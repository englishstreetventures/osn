### Invite styling + contrast warnings + hex picker (claude/cire-invite-styling-picker-87ni7b, 2026-08-01)

Pre-merge security review. **No security findings.** Verified rather than assumed: `ColorPicker.onChange` is called in exactly three places and its argument is always `toHex(...)` (`#RRGGBB`) or `null`, so raw field text never reaches the emit — dropping Kobalte's `ColorField` did **not** widen the CSS-injection surface (IB-S-L1). The new `PARTIAL_HEX` filter is the same language as Kobalte's own `isAllowedInput`, and the new blur commits *nothing* where Kobalte's expanded shorthand, so what can escape is strictly narrower. Both server gates are untouched (`isThemeColor = isSafeCssColor`, still one shared reference, still pinned by `colour-validator-identity.test.ts`). Both new regexes are anchored and bounded (no ReDoS). `paletteContrastWarnings` indexes four hardcoded literal keys and returns numbers and static strings — nothing it produces is interpolated into CSS. No new dependency, route, persisted field or outbound call.

- [x] **C-M1** (fixed on branch) — **the residual-contrast warnings measured the wrong surfaces, so they could stay silent on the copy guests actually read.** `RESIDUAL_PAIRS` measured `--color-surface` under messages naming "event cards", and `--color-surface-raised` under a message naming "pop-ups". It is the other way round on the guest site: `EventCard` is `bg-surface-raised` (as is the RSVP sheet's notice block), while `AnimatedModal` and the sheet's sticky footer are `bg-surface` — and everything on `bg-surface` is already enforced by `derivePalette`. Walking the full (ink, muted, gilt) × (ground, card, raised) matrix, `muted-on-raised` and `gilt-on-raised` were covered by neither enforcement nor warning, which is exactly where every event card lives. **Fixed on branch:** the table now measures the surface each message names, gains `muted-on-raised`, and drops the bloom pair entirely (`--color-bloom` has no render site anywhere in `cire/web`, so it warned about a colour no guest can see). Pinned by a directional test that fails if the two surfaces are crossed again. See [[invite-builder]].
- [x] **C-L1** (fixed on branch) — **the contrast live region re-announced on every pointer-drag frame.** The `role="status"` block was driven by a memo over `previewTokens()`, which is a fresh object per `pointermove`; `role="status"` is implicitly `aria-atomic`, so the whole block — heading, list, advice — was re-read on each frame, and the `<Show>` wrapping the region mounted/unmounted it as warnings flipped. **Fixed on branch:** the region is permanently mounted with its contents conditional, the rows use `<Index>` rather than `<For>` (see [[perf]] **P-W1**), the memo carries an `equals` comparator so an unchanged warning set does not notify at all, and the per-frame ratios are `aria-hidden` — leaving the announced text to change only when the *set of failing pairs* does.
- [x] **C-L2** (fixed on branch) — **the warning told organisers that secondary text "needs 3:1".** `muted-on-ground` used `WCAG_UI_MIN` and printed it verbatim, but every `--color-text-muted` site on the invite is small text (0.74–0.92rem), which WCAG AA puts at 4.5:1 — so a palette at 3.2:1 cleared the check, printed no warning, and failed AA on the guest site. **Fixed on branch:** both muted pairs use `WCAG_TEXT_MIN`. All five curated presets clear 4.5 there (4.65 worst case), so it costs no false alarms.
- [x] **C-L3** (fixed on branch) — **an incomplete hex was discarded on blur with no programmatic notification.** Snapping the field back is visible to anyone watching it and invisible to everyone else, so a screen-reader user could leave the field believing their colour applied (WCAG 3.3.1). **Fixed on branch:** a discard sets `aria-invalid` and posts an `aria-describedby` line naming what was kept ("Needs 6 digits — kept #D4AF37"), cleared as soon as typing resumes.
- [x] **S-H1** (fixed 2026-08-01, `claude/rsvp-notice-contrast-fix-m5px1l`) — **an editor could create co-host seats the owner could not see or remove.** `POST /hosts` had no cap while `hostsService.list` truncates at 200; the pre-merge security review drove it — **211 seats added, 200 listed, 11 live co-hosts invisible to the owner**, and `DELETE` needs a profile id obtainable only from that list. That falsifies the design's load-bearing claim ("every addition an editor makes is reversible by the one person who can't be removed"), and the widened gate turned what used to be self-inflicted into an escalation surface. Amplified by `GET /handle-search` (osnAuth-only), which supplies real strangers' handles. **Fixed:** `MAX_HOSTS_PER_WEDDING = 50`, enforced in `hostsService.add` (409 `host_cap_reached`, own metric label), sitting well below the now-named `LIST_CEILING = 200` so "the list shows every seat" is structural rather than coincidental; `list()` additionally returns the true `total`, and the panel renders an alert when it exceeds the rows shown, so a legacy wedding already above the ceiling can never look complete. Pinned by a cap test and a 205-row truncation test.
- [x] **S-L1** (fixed 2026-08-01) — the widened add route was rate-limited **per IP** while comparable organiser writes use per-user. With the principal set widened from one owner to the owner plus every editor, a per-IP bucket is both weaker against the S-H1 amplifier (rotate IPs) and unfairly shared between co-hosts behind one NAT. **Fixed:** `rateLimitMiddlewareByUser` on both host-write groups, keying the bucket on the identity authorisation now admits.
- [ ] **S-M2** — **a new co-host seat is a silent, immediate grant of guest credentials and Art. 9 data.** Any seat, at any role including `viewer`, reaches `guests.csv` — whose first column is `families.public_id`, the claim code `POST /api/claim` accepts — and `rsvps.csv`, now carrying dietary free text per event. Pre-change only the owner could hand that to a stranger; an editor can now do it unilaterally and the owner is never told. The containment story is "additive, and the owner reverses it", which presupposes the owner learns of it. Mitigated but not closed on this branch: the seat cap (S-H1) bounds the volume, `total` stops the list hiding seats, and `added_by` is now surfaced so an owner *can* see which seats they did not create — but all three are pull, not push. **Fix:** notify the owner (transactional mail via `@shared/email`, which `cire/api` already wires for enquiries, and/or an unread marker on the Hosts panel) whenever `added_by_osn_profile_id !== owner`. Deliberately not done here: cire holds only an OSN **profile id** for the owner, not an address, so the email path needs a new ARC bridge endpoint on osn-api — a cross-service change and a privacy escalation of its own, which deserves its own review rather than a ride-along. The in-app marker is the cheaper half and could land first.
- [ ] **S-M1** — **removal is not terminal: two editors can resurrect each other.** Verified end to end by the review: editor A seats B; the owner removes A; B re-adds A and it succeeds. Nothing records that A was evicted. Against a single hostile editor the asymmetry holds; against one who seated an accomplice it does not, and the owner has no signal that a re-add happened. The owner does have a winning sequence — demote every editor to `viewer`, then remove — but nothing in the API, the panel copy or the wiki says so, which is why the file header's "cannot entrench themselves" was softened rather than left standing. **Fix:** either make eviction sticky (record the removal; refuse a re-add of an owner-removed profile unless the owner performs it), or document the demote-then-remove ordering in the panel and `[[cire-auth]]`. Sticky eviction is new persistent state and a product decision, so it is filed rather than assumed.
- [x] **C-M2** (fixed 2026-08-01, `claude/rsvp-notice-contrast-fix-m5px1l`) — **fixed at the token level rather than by retuning the two presets, because the field report was a CUSTOM palette, not a preset.** A live invite's RSVP-by line measured 3.35:1 (axe / WCAG 1.4.3) — the same defect one DOM level up from the date: `--color-gold` is the metal, held to the 3:1 UI floor by design, and painting normal-size text with it is the bug. Darkening `chapel` and `garden` would have fixed neither. `@cire/theme` now derives **`--color-gold-ink`** — the organiser's own hue walked to `WCAG_TEXT_MIN` against `ground`, `card` AND `raised` (a section's tone is their pick, so any can be the backdrop) — while `--color-gold` stays exactly as chosen for rules, borders, buttons and display headings. The event-card date and the RSVP-by line in both packs use it; `gilt-on-raised` therefore keeps its 3:1 bar legitimately (nothing normal-size is painted in gilt on that surface any more) and the exception comment is gone. `--color-text-muted` moved to the same three-surface text minimum in the same pass — the field palette had it at 4.36:1 behind the *closed* form of that line, and it is a derived grey nobody picks, so enforcing it costs no design fidelity. Pinned by preset sweeps over both prose tokens, a regression test reproducing the 3.35:1 palette, and per-pack class assertions. See [[invite-builder]], [[rsvp-deadline]]. Related: **C-M3** below.
- [x] **C-M3** (fixed 2026-08-01, `claude/rsvp-notice-contrast-fix-m5px1l`) — **the rest of the invite swept onto `--color-gold-ink`.** 45 utility sites across 15 components plus 8 raw-CSS declarations in `SiteFooter.astro` and `LegalLayout.astro`: section eyebrows, control labels (`Add host`, `Respond`, `Add to Calendar`, the Pinterest and map links), modal headings, the consent banner/gate/preferences links, the claim-code notices. The rule applied was **gilt paints borders, fills, icons and large display text; gold-ink paints anything read below the WCAG large-text bar** — and the bar was computed against the SMALLEST size each element can render at, i.e. the `clamp()` minimum times the organiser's `small` heading scale (0.85), not the value read off the class. That distinction decided two cases: gala's claim-section `h2` (`clamp(1.5rem,4vw,2rem)` → 20.4px at `small`) moved to gold-ink, while classic's (`clamp(2rem,5vw,3rem)` → 27.2px) stayed the metal. Five sites keep `text-gold` deliberately — both packs' hero couple names, classic's claim heading, the 404 numeral (all large text) and `MapPreview`'s pin (an SVG icon, a graphical object at the 3:1 bar). `ConsentPreferences`' "Always on" chip lost its `/80` alpha along with the swap: an alpha-modified colour over a surface has no single ratio to enforce, so `text-gold-ink/80` would have looked fixed without being fixed. Pinned by `cire/web/src/styles/gold-text-token.test.ts`, a static source scan whose allow-list is an explicit five-entry list with a stated reason each — deliberately not a size heuristic, since parsing a `calc(clamp(…)*var(…))` to guess whether it clears 24px is the kind of cleverness that fails open. Verified to FAIL when a single `text-gold-ink` is reverted. web 650 → 653. Still open: **C-L5** below.
- [x] **C-L5** (filed then FIXED on the same branch, 2026-08-01) — **`text-gold-dim` painted the hero tagline at 2.05:1, and the first cut of the guard was written never to see it.** Both packs set the couple's subtitle in `--color-gold-dim` at 0.8rem uppercase — normal-size text. That token is the metal at 0.35 alpha and **nothing checks it**: `contrastOklch` ignores alpha by design, because a translucent colour over an unknown backdrop has no single ratio. Composited it measures **2.05:1 on `evergreen`**, the scheme where the undimmed metal clears 8:1 — below even the 3:1 UI floor, and worse than the 3.58:1 that got C-M2 filed. **I deferred this on a premise that was wrong**: "the backdrop is an organiser-uploaded photo, so no palette-level fix reaches it". The hero image is OPTIONAL (`<Show>`-guarded), and with no image the backdrop is the scrim over `--invite-hero-grad-*` — all derived tokens, which a palette-level fix reaches directly. **Fixed:** both taglines moved to `text-gold-ink`. Over a photo it is still strictly better, and the scrim tracks the page's own lightness (dark scheme → dark scrim, light → light), which is the direction this token needs. The guard's exemption is gone too — it now treats `text-gold-dim` AS the metal and catches opacity-modified forms (`text-gold/80`), both verified to fail. Caught by the branch's own pre-PR review, not in production.
- [ ] **C-L4** — **`html { font-size: <px> }` overrides a reader's browser default-font-size preference.** Pre-existing on `main` (the 16px base); this branch only raises it to 17px on desktop, which moves in the accessible direction, and browser *zoom* still scales rem normally so 1.4.4 is satisfied. Worth cleaning up if the rule is ever revisited: express both as percentages (`100%` / `106.25%`) so a reader who has set a larger default keeps it.

### RSVP-by editable by a co-host — review findings (claude/cire-rsvp-date-cohost-edit-va8w9i, 2026-08-01)

Pre-merge security review of the settings field-gate. **No Critical or High findings.** Empirically cleared (probe, not inspection): Effect Schema `Struct` decode strips excess properties, so an unknown key can't ride the patch; a `__proto__` payload is dropped by decode; there are no `fromKey` renames, so wire key ≡ decoded key and case variants don't alias; `weddingIsOwner` is set only by the `weddingEditor` derive from a server-side `hostsService.authorize()` round-trip and **fails closed** if it were ever undefined; the 403 body reflects nothing caller-controlled (`fields` can only hold names from the 7-key schema); the refusal returns before the service, so there is no partial write; and the two scoped `/weddings/:weddingId` groups don't leak derives into each other (a `viewer` still gets `read_only_role` on the PUT). See [[rsvp-deadline]], root wiki `[[cire-auth]]`.

- [x] **S-M1** (fixed on branch) — **the gate enumerated own keys; the writer reads through the prototype chain.** `ownerOnlySettingsIn` decided what a patch carried with `Object.entries(patch)` (own enumerable keys) while `weddingSettingsService.update` decides the same with `patch.displayName !== undefined` (prototype chain). With a pollution primitive anywhere in the codebase the two disagree, and the gate becomes advisory: `ownerOnlySettingsIn` sees nothing, the writer writes `POLLUTED`. Not exploitable today — the obvious sink, the CSV/spreadsheet parser, is clean (fixed literal keys, numeric column indices, no `row[header] = value`) — but the invariant held by accident rather than by construction. **Fixed on branch:** the check iterates `UpdateSettingsBody.fields` and reads `patch[key]`, the same lookup the writer performs, so the two cannot diverge whatever the prototype. Deriving the list from the schema also means a field added to the struct is owner-only from the moment it exists.
- [x] **S-L1** (fixed on branch) — **the full-row read-modify-write let a co-host's deadline save clobber a concurrent owner edit.** `update` read the row and `.set()` all seven columns, so an `editor`'s deadline-only patch rewrote `displayName` / `currency` / `budgetTotalMinor` with values read moments earlier. Before this feature the row had one writer and a race was self-inflicted; with two principals at different privilege levels it meant an `editor` winning a race could silently revert an owner-only field — an indirect write to exactly the data the field gate protects. **Fixed on branch:** the UPDATE names only the columns the patch carries (the deadline pairing rule still fires, but only for a patch that touches the pair), so a deadline-only save is physically incapable of touching owner-only columns. Also closes the perf review's **P-I2** half about the wasted full-row write.
- [x] **S-L2** (fixed on branch) — **a settings change wasn't attributable.** Two principal classes can now mutate a guest-facing control and nothing recorded which one did — an owner who found RSVPs closed had no way to establish they didn't do it themselves (SOC 2 CC6/CC7 attributability). **Fixed on branch:** migration `0056` adds `weddings.updated_by_osn_profile_id` (opaque foreign-system id like `owner_osn_profile_id`, NULL on pre-0056 rows = "unknown", never "the owner"), written on every settings save incl. the budget-total route that shares the service; the refusal branch emits `Effect.logWarning("settings owner-only fields refused", {weddingId, fields})` and increments `cire.wedding.settings.owner_only_refused` — deliberately **attribute-free**, since the field names are already on the log line and putting them on a metric would multiply series for no operational gain (third observability rule). See [[data-map]] for the column's compliance row.
- [x] **S-L3** (fixed on branch) — **no lower bound on `rsvpDeadline`, so a backdated date closed RSVPs for every guest instantly.** `CalendarDate` checked only that the string was a real calendar day, so `1970-01-01` locked the invite the moment it landed — and a guest turned away is told only that RSVPs closed, never that the date moved. **Fixed on branch, for EVERY caller including the owner** (product decision, 2026-08-01): a write that touches the deadline may not leave it already closed → 400 `rsvp_deadline_in_past`. Checked on the RESULTING pair, not on the patch, because either half decides the instant (moving the zone alone can shift an open deadline by ~26 hours), and through `isRsvpClosed` — the single place a date becomes a moment — so the rule cannot disagree with the guest write gate about when a day ends. **Today stays available** (the deadline is inclusive, closing at the end of its day in its own zone), which is what an organiser wanting to stop taking replies actually needs; a deadline that lapsed naturally is untouched by patches that don't name it, and can still be cleared. Mirrored client-side so the mistake never round-trips.
- [ ] *Noted, not a finding:* `canEdit = () => props.wedding.role !== "viewer"` (`OrganiserApp.tsx`) is fail-**open** on an unexpected role string and now feeds `canEditRsvpDeadline`. Pre-existing and client-side only — the server normalises unknown roles to `viewer`, so the worst case is rendering a control whose save 403s.

### Closing hero band — review findings (claude/closing-hero-image-j40coh, 2026-07-31)

Pre-merge security review of the closing image's move to a full-bleed band. **No Critical or High findings.** Confirmed unchanged: no `cire/api` file is touched, so the S-H1 claim gate holds exactly (`getForSlug` still redacts `footer`, `slotRequiresSession("footer")` is still true, `sessionOwnsWedding` still binds the session to the wedding, still 404 rather than 403); CSS injection stays closed at the sink (`cssUrlValue` escapes `\` and `"` and strips control chars before `url("…")`, and Solid's `setProperty` makes a stray `;` an invalid value rather than a second declaration); crop JSON is still validated at the write (`isValidCrop`), on read (`decodeCrop`) and again client-side (`isRenderableCrop`); and `hero` was already in the bounded `IMAGE_VARIANTS` allowlist, so transform cardinality is unchanged. See the root wiki's `[[invite-builder]]`.

- [x] **S-L1** (fixed on branch) — **a crop-derived `aspect-ratio` could be a value CSS cannot parse.** `cropAspectRatio` required only that `natW`/`natH` be positive and finite — the same bar the API sets — so a wedding editor could persist `natW: 1e308, natH: 1e-300`, whose ratio stringifies to `"1e+308"`. CSS rejects exponential notation, the declaration is dropped, and the band renders as a zero-height box for every guest of that wedding. Scoped to a wedding the actor already controls (hence Low), but the band and the organiser preview both consumed it. **Fixed on branch:** both `cropAspectRatio` mirrors clamp to `[0.05, 20]` and fall back to the slot default outside it, so the bound sits where the value is produced. Pinned by a test in each package.
- [ ] **S-M1 / P-C2** — the gated closing image's transform is never edge-cached (`Cache-Control: private` refuses the `cache.put`), so every guest scroll to the now-full-bleed band is one uncached, billed Cloudflare Images call — and this branch moves each call from 320w to 1600w. The gate itself is not bypassable; the COST is. Fix belongs in `@cire/api` and is deliberately not taken on this branch — full write-up in [[perf]] **P-C2**.
- [ ] **S-L2** — **cropping is presentational, not redaction.** The crop is rendered entirely in CSS; `GET /api/invite/:slug/image/footer` always serves the whole image, width-transformed only, so any claimed guest can strip the crop by fetching the URL. Organisers reasonably read "crop" as "remove". Pre-existing, but this branch is what turns the slot into the place couples put photographs and puts the result at viewport scale. No code change here — note that the 1∶1 → 16∶9 legacy fallback strictly *reduces* over-reveal, and the footer slot postdates `natW`/`natH` capture so that path is near-unreachable in production. Worth doing: say plainly in the crop editor's copy that cropping changes framing, not what is stored or served, and file real region-cropping on upload (or a Cloudflare Images region transform) if organisers should be able to actually remove content.

#### Compliance

- [ ] **C-M1** — **a viewport-spanning photograph is still marked purely decorative.** Both paths keep the pre-branch treatment (`alt=""`, and `aria-hidden="true"` on the crop layer) and there is no alt-text field for the slot, while the branch changes its purpose from "monogram, motif or signature" to the invite's closing image at up to 85% of the viewport. `alt=""` is correct for genuinely decorative imagery; a screen-reader user now gets nothing where a sighted guest gets most of the page (WCAG 2.2 SC 1.1.1 / EN 301 549 / EAA). The 200px square made the decorative claim defensible; the band does not. Fix: either add an optional alt/caption alongside `footer_image_key` (surfaced as `alt` and as `aria-label` on the crop `div`), or keep `alt=""` and state the consequence explicitly in the builder copy — and record the decision in `wiki/compliance/` so the position is deliberate rather than inherited. The existing mitigation (the note field) only works if organisers duplicate the image's meaning into it, which the copy asks for but nothing enforces.
- [x] **C-L1** (fixed on branch) — the organiser preview announced the closing image on the crop path (`role="img" aria-label="Closing image"`) and hid it on the no-crop path (`alt=""`), so whether a non-sighted organiser heard about their own content depended on whether a crop happened to be saved. **Fixed:** both preview branches carry the same accessible name. The GUEST band stays decorative on both paths pending C-M1 — this is a preview, where "the band exists and is populated" is the point.

### Single-sheet CSV uploads + import error reporting — review findings (claude/cire-dashboard-csv-uploads-zk5rt0, 2026-07-31)

Pre-merge security review of the partial-upload branch. The five nominated areas came back clean: multi-tenant scoping is unweakened (the three reads skipped under `scope='events'` are replaced by `[]`, not by dropping a predicate), authorisation is intact (no single-sheet-specific route; apply reads `scope` from the persisted row, and `ApplyBody` is `{importId}` only, so a caller cannot widen scope at apply), the "absent sheet ≠ empty sheet" invariant holds against a crafted `{"guestsCsv": ""}` body (422, households intact), and `stripBom` opens no formula-detection bypass (`header.map(h => h.trim())` already strips U+FEFF — it is in the ECMA-262 `WhiteSpace` production). Fixed on branch below; the two open items are pre-existing gaps this branch made more reachable. See [[guest-event-editor]] §3.1, [[api]].

- [x] **S-L1** (fixed on branch) — **`parseErrorBody` reflected the throw site's source column into the 422 body.** `MalformedSpreadsheet` declared `column?: number`, but `Data.TaggedError` extends `Error` and JavaScriptCore stamps its own `line`/`column`/`sourceURL`/`originalLine`/`originalColumn` onto every instance — so a construction site that left `column` unset did not read back `undefined`, it read back JSC's value, and `e.column ?? null` reflected it. Verified: an empty-sheet 422 returned `column: 37`. Production runs on workerd/V8, which has no such own property, so the disclosure was confined to the Bun local/dev entry — but the organiser-facing consequence (`formatImportError` rendering "In your guests sheet, column 37" for a whole-file failure) was a contract defect on any runtime. **Fixed:** the optional coordinates are renamed `atRow`/`atColumn`, out of the collision entirely; the wire names stay `row`/`column`. `FormulaInjectionDetected` keeps `row`/`column` — they are REQUIRED there, so the constructor always overwrites whatever the runtime stamped. Regression tests at both the parser and route layers assert the coordinates come back absent/null for a whole-file failure.
- [x] **S-L4** (fixed on branch) — `stored.scope` was type-asserted out of the row's `summary` JSON and passed straight into `diffAgainstDb`. It failed safe only incidentally (an unrecognised string leaves both `manageEvents`/`manageGuests` true, so an `""` slot 422s rather than deleting) — safety resting on `!==` comparisons rather than on the value being one of three literals, which a refactor to `scope === "both" ? …` would silently invert. **Fixed:** decoded through the `ChangeScope` `Schema.Literal` with an explicit `"both"` default.
- [x] **S-L5** (fixed on branch) — **legacy revert could feed an editor DesiredState JSON blob to `parseEventsCsv`.** `reconcileToSnapshot`'s new blank-half inference is byte-based, and the legacy prior-row selection filtered only on `status='applied'`. A `kind='editor'` row holds JSON in the events slot and `""` in the guests slot — byte-wise indistinguishable from an events-only upload — so the inference yielded `scope: "events"` and fed JSON to the CSV parser. Reachable because `pruneBeforeImages` NULLs the before-image keys beyond the most recent 10 changes, pushing ordinary rows onto the legacy path. It failed safe only by luck (no cell normalises to `Event Name`); a blob that DID parse would have wiped the schedule. **Fixed:** the legacy selection filters `eq(imports.kind, "import")`. Covered by a revert test that plants an editor row between two imports and asserts the rollback skips it.
- [x] **S-L6** (fixed on branch) — the organiser's `formatImportError` indexed `SHEET_LABEL` with a `sheet` value cast from `res.json()` and never validated, so a body carrying `sheet: "constructor"` returned a function that `capitalise()` then threw on. **Fixed:** explicit two-literal check.
- [x] **S-L2** (partially fixed on branch) — `UnmatchedEventColumn.column` is raw uploaded header text (pre-existing reflection), and the new `parseErrorBody` docstring asserted the reason-lockdown contract "keeps sheet data out of API responses", which is not true of that field. Not XSS — the organiser app has no `innerHTML`/`set:html` sink anywhere and SolidJS escapes the `{error()}` text interpolation — but an over-broad contract claim is exactly how a later HTML-based error renderer or log-forwarding sink becomes an injection. **Fixed:** the reflected label is truncated to 64 chars (a cell may be up to `MAX_CELL_LENGTH` = 10 000), and the docstring now enumerates which fields are static, which are untrusted-but-reflected, and which are withheld.
- [ ] **S-M1** — **the DesiredState front door skips `isIsoTimestamp` / `isFormulaCell`, and a poisoned event row breaks downstream consumers.** `ParsedEvent.startAt`/`name` are bare `Schema.String`, so the editor front door writes free text that the CSV parser would refuse; `applyImport` stores it verbatim. Pre-existing and out of scope for this branch, which touches only the spreadsheet door. **The specific symptom this branch would have introduced is fixed**: `currentEventsAsParsed` no longer round-trips DB rows through `parseEventsCsv`, so a poisoned row (or a legitimate `-12 Smith Street` address) can no longer break guests-only upload/apply/revert. The underlying validation gap remains — wire the shared rules from `guest-event-validation.ts` into the DesiredState schema (`Schema.filter(isIsoTimestamp)` on `startAt`/`endAt`, reject `isFormulaCell(name)` and blank `name`/`timezone`) to restore the parser-parity invariant in [[guest-event-editor]] §3/§9. Related: **C-M1** below.
- [ ] **S-M2** — **a header-only single sheet is still reconciled as "delete everything".** The empty-sheet guard fires only on `rows.length === 0`; a file with a valid header and no data rows parses to `[]` and is authoritative. Verified: a header-only guests sheet previews 200 with `familyRemoves: 1, guestRemoves: 1` — every household queued for deletion along with its claim codes and RSVPs. Pre-existing for two-sheet uploads, but materially more reachable now that dropping in one file is the intended flow (a downloaded-but-unfilled template, a mis-picked tab on Excel's "Save As CSV", a filtered-then-exported view). Preview/apply is a good TOCTOU control but a weak *intent* control — it does not distinguish "I meant to delete 40 households" from "I uploaded the wrong file". Options: reject a data-row-less sheet with a new static reason, or gate a ≥N% removal behind a `requiresConfirmation` flag that apply must echo. Left open deliberately — it is a product decision about a destructive-op guard, not a defect in this branch.

### Site-wide consent framework (`claude/site-wide-consent-framework-jys0q2`)

From the /prep-pr Step 6 security review (2026-07-29). **No Critical, no High.** The
gate was confirmed to prevent the third-party request rather than merely hide output
(`<ConsentGate>` doesn't render children, so `PinterestEmbed`'s `onMount` injection never
runs), nothing security-relevant is trusted from the consent cookie, and no CSP change
was needed or made.

- [x] **CON-S-L2** (fixed on branch) — `vendor.privacyUrl` rendered into `<a href>` by both the preferences dialog and `/privacy` with no scheme validation. Not exploitable today (values hardcoded) but the registry is the documented "add a vendor here" extension point, so a `javascript:`/`data:` URL added later became a same-origin script sink. `vendors.test.ts` now fails the run unless every `privacyUrl` is `https://`.
- [x] **CON-S-L3** (fixed on branch) — the prototype-pollution regression test was a **false negative**: it passed `__proto__` in an object *literal*, where it is a prototype setter rather than an own property, so `Object.entries` never saw it and the test would have passed against unsafe code. Now driven through `JSON.parse` / `decodeConsentRecord`, which is the shape a tampered cookie actually delivers. (The code was, and is, genuinely safe.)
- [x] **CON-S-L4** (fixed on branch) — `decidedAt` is documented as the Art. 7(1) audit trail but was accepted as any string. Now fails closed on an unparsable date, an empty string, a non-string, or anything over 40 chars — the same treatment the version fields already got.
- [ ] **CON-S-M1** — **withdrawing consent does not tear down third-party code that already ran.** Flipping a category off unmounts the embed and removes the injected `<script>` (asserted by test), but `pinit_main.js`'s already-executed globals, listeners and any storage it set survive the rest of the visit. Under the new **opt-out** defaults this is the *common* path, not an edge case: the banner appears after the embeds have loaded, so "Reject all" is nearly always clicked with third-party contexts live. **Partially addressed on branch** — the preferences dialog now states the residual plainly ("to also clear content already loaded during this visit, reload the page"). The full fix is a `location.reload()` on a granted→revoked transition for any category with `enforcement: "gated"` vendors. Deliberately not done here: a reload is user-visible and can discard in-progress page state, and it must only fire when the cookie write actually succeeded (else the refusal is lost on reload). See `[[consent]]`.
- [ ] **CON-S-L1** — `cire_consent` is not `__Host-`-prefixed, so a script on a sibling `*.cireweddings.com` origin can set a `Domain=.cireweddings.com` cookie of the same name; `readConsentCookieValue` returns the first match and browser ordering between domain and host-only cookies of equal path is unspecified. A guest's stored *refusal* could be silently overridden back to "allowed". Integrity attack on a privacy decision, not a credential. Fix: write `__Host-cire_consent` when `secure` (the attributes already satisfy the prefix), fall back to the bare name on http dev, read both preferring the prefixed one. See `[[consent]]`.

Accessibility/compliance findings from the same review (cire has no compliance shard; both are fixed on
branch, so they are recorded here next to the review that found them rather than opening one):

- [x] **DND-C-M1** (fixed on branch) — **the replacement keyboard path was invisible to Windows screen readers.** The grip's only keyboard affordance was a bare `ArrowUp`/`ArrowDown` `keydown` handler, and NVDA/JAWS run in browse mode by default, consuming unmodified arrow keys for their own virtual cursor — they forward them to a plain `<button>` only in focus mode, which buttons don't trigger. A screen-reader user would tab to the grip, read the `aria-describedby` hint telling them to press the arrows, press them, and get nothing, with no discoverable alternative. The ▲/▼ pair this list replaced was Enter/Space-activated, which browse mode **does** forward, so this was a straight **WCAG 2.1.1 / EN 301 549 regression** against the thing it replaced — and it silently undercut the whole point of the branch's announcement work, since a user who can't trigger a move never hears one. Fixed by keeping an Enter/Space-operable path as `sr-only` "Move X up/down" buttons per row (reusing the same `handleKeyboardMove` and live region, so wording stays consistent across all three input paths), `focus:not-sr-only` so a sighted keyboard user never focuses an invisible control (WCAG 2.4.7), and `disabled` at the list ends so AT reports the boundary. The **visible** ▲/▼ pair stays gone — the visual UI is drag-only as intended. See `[[architecture/drag-and-drop]]`.
- [x] **DND-C-L2** (fixed on branch) — the grip was ~18 CSS px tall (`px-1` + `leading-none`, no vertical padding) on the row's only re-order affordance, under the **WCAG 2.5.8** 24 px minimum.
