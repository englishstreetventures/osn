Session revoke, consent re-grant, passkey counters and erasure cancel hold against a request that lands between their read and their write.

- `DELETE /sessions/:id` revokes the device: every session in the family of the session its handle names, deleted in one statement. A handle the device has since refreshed past still finds its family, through the rotation records. A refresh rotation inserts the new session (copying the device and any restriction from the old row as it stands) before it deletes the old one, so a revoke, a reuse revoke or any account-wide sign-out that lands mid-rotation leaves no session behind it. A failed rotation keeps the old session. A grant that loses its swap removes what it wrote and answers the race message, as a concurrent grant does.
- Re-approving an OIDC consent writes the merged scope only while the consent is as it was read. A revoke landing in between makes the approval start from exactly the scope it approved, never the withdrawn one; a second change in that window fails the approval with a 500 and writes nothing.
- A passkey assertion's counter is written only while the stored counter still lets it through (below the new one, or both 0). Of two assertions verified against one counter, the second to write is refused with `Passkey verification failed` at sign-in and at step-up, as it is when they arrive in turn; a passkey deleted between the read and the write is refused too.
- `deletion_jobs` gains `purge_started_at` (migration `20261030093003_deletion_job_purge_claim`). The fan-out and hard-delete sweeps stamp it before they purge anything; `POST /account/restore` cancels only while it is unset and the grace window is open, in the same statement, and answers `{ cancelled: false }` otherwise. A cancel that lands first leaves the sweep nothing to purge.
- A cancel deletes only the job it read, and records one `account_deletion_cancelled` event per job: the event's id is derived from the account and the job, so of two cancels of one job the second answers `{ cancelled: false }` and writes nothing, and a cancel that read a job since cancelled and asked for again leaves the new job standing.
- Sign out everywhere else, passkey add and delete, email change and erasure keep the caller's device, the whole session family of the live session the request named, not that one session id. The caller stays signed in through a refresh of that session in flight in another tab. A session already rotated out when the delete runs spares nothing, so a stale token cannot shield its family.
- `POST /logout` ends the device: every session in the family of the session the cookie names, found from the live session or from the token's live rotation record, so a refresh of the same token in another tab cannot leave a session behind. `DELETE /sessions/:id` answers `revokedSelf` by that family, so the cookie is cleared when the caller's device went, whichever of its sessions the cookie holds. The restriction lift at passkey enrolment covers the whole family of the caller's live session, so a refresh in flight cannot leave its new session restricted.
- `osn.auth.session.family_revoked` and its warning count a reuse revoke only when it removed a session; a stale replay whose family is already gone counts `reuse_detected` and logs at info.
- `GET /sessions` marks `isCurrent` on the caller's device, the family of the session the cookie names, so a cookie the device has refreshed past still marks its live session.
- `POST /logout` with a token rotated out more than the grace window ago counts as reuse, as `/token` does: `reuse_detected`, then `family_revoked` and a warning when it removed a session, and it deletes the family's rotation records so one token counts once.
- `verifyRefreshToken` drops `createdAt`, `uaLabel` and `ipHash` from what it returns; no caller read them.
- On bun:sqlite, a rotation that cannot remove its own new session after a failed write logs it at error, annotated with whether the session was restricted.
