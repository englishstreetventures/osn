# cire/api

Backend feature work. The Elysia + Effect + Drizzle layer in `cire/api`.

- [x] **`GET /api/claim/session` — restore an invite from an existing household session** (`claude/invite-code-gating-hints-g8nw0o`, 2026-08-02) — a `cire_session` lasts 30 days, but `POST /api/claim` was the only door in, so a household that had already opened its invite retyped its code on every visit and the events list arrived only after they did. The new read is gated by `sessionAuth()` and keyed on the cookie-derived `familyId`: it accepts **no** claim code and the caller cannot name a family, so it asks "what is MY invite", never "whose invite is this" — not a second credential surface. It re-checks `families.deactivated_at` as defence in depth (deactivation already revokes the family's live sessions in the same commit, so this is the belt to that braces) and clears the stale cookie on that 401 instead of leaving a household retrying a dead one; and it skips the first-open write, which by definition is not what a restore is. Both entry points now build through one shared `buildClaimResponse`, so the events list and the S-H1-gated closing section cannot drift between claim and restore. Scoped to the wedding being rendered via a required `?slug=` + `inviteService.sessionOwnsWedding` (S-M1), and answered `Cache-Control: no-store` + `Vary: Origin, Cookie` from a hook ahead of `sessionAuth` (S-H1). Mounted as a **sibling Elysia instance** (`createClaimSessionRoutes`) rather than another method on the claim route, because a scoped limiter applies per instance: sharing the claim endpoint's 5/min brute-force budget would have made a household 429 itself just by reloading. Its own `claimSessionLimiter` is 60/min, mirroring `oidcSessionLimiter`; a test pins that a spent claim budget leaves the restore working. Its 60/min budget is a real edge limiter: a second native ratelimit binding (`CLAIM_SESSION_RATE_LIMITER`, namespace 1002) declared top-level **and** under `[env.production]` — named envs do not inherit — and wired in `index.ts`, which the first cut forgot, leaving production on a per-isolate in-memory fallback (P-W4). api 1421 → 1468. See [[cire-auth]], [[web]], [[security]], [[perf]].
- [x] **Co-host autocomplete is driven by the organiser's OSN connections** (`claude/cire-cohosts-autocomplete-z5l9ew`, 2026-08-02) — the add-co-host input previously autocompleted against the **global** handle namespace only, which is the wrong first source: a wedding's co-hosts are nearly always people the organiser already knows on OSN, and a global prefix scan makes the person they mean compete with strangers holding confusable handles. `GET /api/organiser/handle-search?q=` now merges two ARC (`graph:read`) sources — the caller's own connections first (flagged `connected: true`), the global prefix search second — deduped, self-filtered, capped at 8. New osn-api `GET /graph/internal/connection-search?profileId=&q=&limit=` backs the first: accepted connections only, `profileId` taken from the caller's own token `sub` (never client-supplied), matching on handle prefix **or display-name substring**, **no minimum query length** — a single accepted-connection list has no namespace to enumerate, so the empty query is legal and returns the first page, which is what lets the portal open its dropdown **on focus, before a keystroke**. New `osn-bridge.ts` `createArcConnectionSearchResolver` / `createConnectionSearchResolverFromEnv`, injected via `createApp({ resolveOsnConnectionSearch })` with the same key-optional guard as its siblings. **Fail-soft per source, independently caught**: one lookup failing degrades only itself (lose connections and handle-typing still works; lose the global search and the connections still show), never a 503/500. `HostsPanel.tsx` opens the dropdown on focus with a "From your OSN connections" caption, badges connections in a mixed list, and drops its client-side 2-char floor. **No new ARC scope and no migration** — reuses `graph:read` and the existing `connections_requester_idx` / `_addressee_idx`. ⚠️ **Deploy-time**: osn-api must redeploy to serve the new endpoint; until it does, cire falls back to the global search alone (fail-soft, no error). See `[[wiki/systems/cire-auth]]` (root).
- [x] **A deleted guest could come back — row identity in the reconcile diff** (`claude/cire-guest-deletion-bug-ve85ng`, 2026-08-02) — reported from the live wedding: "when trying to delete guests they aren't deleted; when reloaded the deleted guest comes back". The editor has no delete verb — it posts the whole draft and a deletion is the row's ABSENCE — so anything that keeps an existing row reachable-but-unmatched, or lets a surviving desired row adopt it, is a delete that silently never happens. Three defects in `diffAgainstDb`, all of which apply cleanly and report success:
  1. **A first-name collision inside a household made a guest undeletable.** The per-family collection the removal scan reads was a `normFirstName → guest` map, so a household holding `Sam` and `sam ` (or two `Guest`s) kept only one of them in it. The other was invisible to the scan — drop it from the draft and the plan emitted **no op at all**. It was invisible to the link pass too (which keyed resolved ids by `(familyId, normFirstName)`), so both twins resolved to one id: one collected both link sets and the other's event invitations were diffed away on every save. The scan now reads the household's full guest LIST and the link pass keys by parsed POSITION; name matching became a per-name queue each desired row consumes from, so a duplicate roster also re-imports idempotently instead of churning.
  2. **`matchByName` is now a property of the front door.** Ids resolve first across the whole household, then names fill in the rest — but only for a spreadsheet, where an absent id means "this sheet has no id columns". For the editor an absent id means "just added", so name fallback is off: deleting `Bo` and adding a different `Bo` in one save used to resolve the new row to the deleted one, emitting no `guestRemove` and handing the newcomer the deleted guest's RSVPs. Decided in `decodeChangeBody`, persisted on the change summary, re-read at apply so the TOCTOU re-diff matches as the preview did (legacy rows fall back to `kind !== 'editor'`).
  3. **An existing row is claimed at most once.** Two desired households resolving to one existing row reconciled against its guest list twice in a row, and the second pass removed every guest the first had just matched.
  4. **A stale draft is refused, not applied** (S-M1, found by the pre-merge security review). `baseRevision` guards preview→apply; nothing guarded LOAD→preview, and turning name fallback off made that window destructive rather than merely stale — a draft row whose id a co-host deleted in between became a REMOVE plus a CREATE, dropping that row's RSVPs and returning a household under the `publicId` the draft still carried, resurrecting an invite someone had deliberately revoked. An id resolving to nothing (or, for a guest, to another household) now fails the diff with `StaleDesiredState`; both verbs answer 409 `stale_draft`. A sheet's dangling id is untouched — there it means "no id columns", and name matching is the design.
  5. **A carried claim code can no longer fail an INSERT mid-apply** (S-L4). `families.public_id` is globally unique and a create may bring its own (`Family Code`), so a taken code violated the constraint *during* `applyImport` — which commits in ≤50-statement chunks and stamps the before-image in the LAST batch, leaving a half-written wedding with nothing to revert to. The diff now mints a fresh code and warns; codes freed by the same plan's removals stay reusable.
  Also `GET .../households` (`weddingMember()`, `claimService.getAllHouseholds`) — the household-shaped roster read. `/guests` is guest-shaped, so a household holding no guests produces no rows and cannot be described by it; the editor's draft is the whole truth, so such a household read as deleted and the next save removed it **and its live claim code**, having never shown it. Both editors now load it. It counts guests in SQL (`count()` + `GROUP BY`) rather than fanning the LEFT JOIN out one row per guest (P-W1), is `Cache-Control: no-store` — `families.public_id` is a CREDENTIAL in the data map and every other response carrying it already was (S-L2) — and logs its defects like the CSV exports (S-L3); `/guests` was given both alongside it. The apply-time `matchByName` read is DECODED rather than asserted (S-L1): `??` guards only nullish, so a corrupt falsy value would have turned an IMPORT re-diff id-authoritative and made every id-less sheet row a create. `import.identity.test.ts` pins the rules (5 of its first 6 cases fail on the old diff), with the event-side equivalents, the pass-1-before-pass-2 ordering, and a `matchByName: false` fixpoint; route tests walk the delete end-to-end through preview + apply, incl. the apply-time re-diff and a summary rewritten into its pre-branch shape (the deploy-window row). api 1435 → 1449. See [[guest-event-editor]] §3.2.
- [x] **RSVP CSV: dietary is a column PER EVENT** (`claude/rsvp-notice-contrast-fix-m5px1l`, 2026-08-01) — reported from the live wedding: a guest was marked "fish only" for the mehendi and the download showed no dietary note for them at all. `rsvps.dietary` is stored per (guest, event) — one reply per event, each with its own field — but `toCsv` emitted a single aggregate `Dietary Requirements` column filled by scanning the guest's replies in event order and taking the **first non-empty** one. Any guest with notes on two events silently lost all but one, and which one survived depended on event start times. There is no correct winner to pick: a guest who eats fish at the mehendi and is vegetarian at the reception has two true answers and each event's caterer needs their own. `RsvpExportRow.dietary` is now `string[]`, index-aligned with `cells` and `RsvpExport.events`, and the CSV interleaves the pair — `<Event>`, `<Event> Dietary` — rather than appending a block of dietary columns after the statuses, so the person catering one event reads its status and its note side by side and adding an event inserts two adjacent columns instead of one in each of two distant places. The aggregate column is **gone**, not kept alongside: keeping it would have kept the lossy value on the sheet. A dietary cell blanks on exactly the condition the status cell blanks on (guest not invited), so a reply that outlived its invitation can't show a requirement beside an empty status. The in-dashboard RSVP view (`buildView`) was already per-event and is untouched — which is why the organiser could see the note in the portal but not in the download. Three tests: per-event alignment, the two-different-notes field case asserted through to the CSV columns, and the uninvited blanking; plus a row-width assertion that catches an off-by-one in the interleave. api 1417 → 1419.
- [x] **An `editor` co-host can ADD co-hosts** (`claude/rsvp-notice-contrast-fix-m5px1l`, 2026-08-01) — asked for directly: "make it so editor cohosts can add more cohosts", from an organiser who was the bottleneck on handing out claim codes for a wedding three people were running. `POST /hosts` moves from `weddingOwner()` to `weddingEditor()`; `DELETE /hosts/:osnProfileId` and `PUT /hosts/:osnProfileId/role` **stay owner-only**, so the route file now carries two `.group("/weddings/:weddingId")` blocks under different gates (a gate applies per group). The line is additive-versus-subtractive, not read-versus-write, and it is what makes this safe rather than a privilege ladder: `editor` is the ceiling of what anyone can grant (`role` is `editor | viewer`, and the owner is never rowed into `wedding_hosts`), so an editor adds a **peer**, never a superior; and because demotion and removal stay with the owner, an editor cannot evict the owner's other co-hosts, cannot demote a rival, and cannot entrench themselves — every seat they create is reversible by the one person who cannot be removed. **The gate swap alone would have shipped a real bug**: the handler passed the caller's own `osnProfileId` as BOTH `addedByOsnProfileId` and `ownerOsnProfileId`, which was only ever harmless because `weddingOwner()` made them the same person. With an editor calling, the service's `owner_is_host` check would have compared the owner's id against the EDITOR's, missed, and rowed the owner in as a co-host of their own wedding — after which a later "remove host" would appear to strip them. `weddingEditor()` now derives `weddingOwnerOsnProfileId` (free — `authorize()` already reads the column) and the two ids are passed separately, so `added_by` credits the actual adder. Portal: `HostsPanel` splits `canManage` into `canManage` (owner: role flip + remove) and `canAdd` (owner or editor: the add form), wired from `ModuleShell`'s existing `canEdit` — the two flags mirror the two gates so the UI never offers a button the API would 403. Tests: the obsolete "403 for a CO-HOST" case is replaced by editor-adds-201 (asserting `added_by` is the editor), editor-grants-viewer, editor-re-adds-owner-409 (the bug above, pinned), and viewer-gets-`read_only_role`; the existing editor-cannot-DELETE and editor-cannot-PUT-role cases already pin the other half. api 1414 → 1417, organiser 662 → 663. **Pre-merge security review then found the design's load-bearing claim was false and it was fixed on branch (S-H1):** `POST /hosts` had no seat cap while `list()` truncates at 200, so an editor could create co-hosts the owner could neither see nor DELETE — 211 added, 200 listed, 11 unreachable. `MAX_HOSTS_PER_WEDDING = 50` now sits below the named `LIST_CEILING = 200`, `list()` returns the true `total` and the panel alerts when it exceeds the rows shown, and `added_by_osn_profile_id` is surfaced so an owner can see which seats they did not create. The limiter moved per-IP → per-user (S-L1). Left open and filed: **S-M2** (a new seat is a silent grant of the household claim codes and the Art. 9 dietary export — owner notification needs an osn-api email bridge that does not exist) and **S-M1** (two editors can resurrect each other; the owner's winning sequence is demote-then-remove, now documented rather than assumed). See [[cire-auth]], [[security]].

- [x] ~~Set `Domain=` on session cookie when production root domain lands~~ — **Audited (no `Domain=` needed) `feat/cire-assets-reconcile`.** The `cire_session` cookie is HttpOnly + `SameSite=Lax` + host-scoped (no `Domain=`, `buildSessionCookie` in `lib/cookie.ts`).
