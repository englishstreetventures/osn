# `@cire/db`

Drizzle schema, migrations, and dev-seed for the Cire D1 database.

## Layout

```
cire/db/
├── src/schema.ts         # Drizzle schema — single source of truth
├── drizzle.config.ts     # Drizzle Kit pointer to schema + migrations dir
├── migrations/           # Forward-only D1 migrations (committed)
│   ├── 0001_initial.sql  # THE BASELINE — the whole schema in one file, generated
│   └── <YYYYMMDDHHMMSS>_<name>.sql  # every migration since, one file each (see below)
├── migrations-archive/   # the chains the baseline stands for; Wrangler never reads them
│   ├── 0001_… – 0081_…   # the original chain, which production ran first
│   └── long-lived/       # every migration a squash moved out of migrations/, under the
│                         # names and with the bytes dev's and production's ledgers hold
├── seed/
│   ├── data/             # Canonical seed data (single source of truth)
│   │   ├── events.ts     # keyed-by-slug sample events
│   │   ├── guests.ts     # sample families + guests (stable UUIDs)
│   │   ├── wedding.ts    # bootstrap wedding row + DEV_OWNER_PROFILE_ID
│   │   └── index.ts      # re-export — `@cire/db/seed`
│   ├── generate.ts       # derives dev-seed.sql from ./data
│   └── dev-seed.sql      # GENERATED dev seed (events + families + guests)
└── tests/seed/
    ├── seed.test.ts      # fails CI if the generated .sql drifts from its source
    └── seed-applies.test.ts  # applies the seed to the migrated chain
```

## Scripts

Run from the repo root with `bun run --cwd cire/db <script>`. Wrangler reads
`cire/api/wrangler.toml` via the `--config` flag baked into each script. The
two scripts that apply migrations go through `scripts/cire-db-migrate.ts`,
which checks the target's ledger first (see the baseline section below) and
runs the wrangler `cire/api` installs from the lockfile. Without that install
it stops rather than fetch another version. Both target the local database: the
script refuses `--remote`. The cire stack migrates the dev and production
databases with Alchemy (`wiki/shared/production-deploy.md` §4).

| Script             | What it does                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------- |
| `db:generate`      | `scripts/db-generate.ts` — diff the working tree's `schema.ts` against `HEAD`'s, write one migration file (see below) |
| `db:push`          | Check the ledger, then apply pending migrations to the **local** D1 (Miniflare-backed)            |
| `db:migrate:local` | Same as `db:push`                                                                                 |
| `db:seed`          | Apply `seed/dev-seed.sql` to the local D1 (re-runnable — `INSERT OR IGNORE` skips rows already there) |
| `db:reset`         | Wipe local D1 state, re-run migrations + seed. Destructive — local only.                          |
| `db:studio`        | Launch Drizzle Studio for browsing the schema / writing one-off queries                           |
| `seed:generate`    | Regenerate `seed/dev-seed.sql` from `seed/data/`                                                  |
| `test`             | Run the seed sync test (`bun test`) — fails if the generated `.sql` is out of sync                |

The remote script names its target database explicitly **and** passes `--env`.
Neither is optional: without `--env`, wrangler resolves the name against the
top-level config, the local `wrangler dev` binding, whose `cire-db` block
carries the production database id.

The dev tier's database is not migrated or seeded from here: the cire stack
(`cire/infra`) creates it in the dev account, applies the migrations, and
imports `seed/dev-seed.sql` on the first dev deploy and again whenever the file
changes.

Production is never reset and never seeded — no script here can do either.

### Typical flows

**First-time setup**

```bash
bun install
bun run --cwd cire/db db:reset   # creates local D1 from scratch and seeds it
bun run --cwd cire/api dev
```

**After editing `schema.ts`**

```bash
bun run --cwd cire/db db:generate --name <snake_case>
#   writes cire/db/migrations/<YYYYMMDDHHMMSS>_<name>.sql; add a rationale
#   header comment and review the SQL, without changing the shape it creates
bun run --cwd cire/db db:push       # applies it locally
# mirror the change in cire/api/src/db/setup.ts's DDL string — the
# ddl-lockstep test fails until all three surfaces agree
```

### The baseline, and why its filename matters

`migrations/0001_initial.sql` is not the first migration — it is the **whole
schema**, generated by `scripts/cire-db-baseline.ts` from a replay of
`migrations-archive/long-lived/`. It builds exactly what that chain builds, and
what the original chain in `migrations-archive/` builds followed by the
long-lived chain's migrations; `cire/api/tests/db/ddl-lockstep.test.ts` replays
all three and fails if a single table, index or trigger differs. D1 bills a
from-zero build per schema statement, even against empty tables. The original
chain spends 351 of them, most on SQLite rebuilding whole tables for `ALTER
TABLE ... DROP COLUMN`, and the long-lived chain 200; the baseline spends 150,
one `CREATE` per table, index and trigger. `scripts/guard-d1-migration-cost.ts`
prices the live chain against the free tier's 100,000 rows written a day.

*Measured 2026-11-19 — `bun run scripts/guard-d1-migration-cost.ts --all` for
the baseline; each archive through the same script's `measureChain`.*

**Only a new database runs it**: a local one, or an investigation stage's.
Dev and production recorded the long-lived chain's own `0001_initial.sql`, the
baseline before this one, by name and hash, so the cire stack hands them the
long-lived chain instead (below).

**Do not rename it.** Wrangler skips any file already named in a local
database's `d1_migrations` ledger. Every local database an earlier chain built
holds `0001_initial.sql`, so the baseline is skipped there and only what follows
it applies. Under any other name it would run the whole schema against that
database and fail on the first `CREATE TABLE`. `ddl-lockstep.test.ts` pins the
name. Nor change its bytes outside a squash: Alchemy records each applied
file's hash, and an investigation stage built from this baseline would be
refused.

**Apply local migrations only through the scripts above.** Skipping the baseline
is right only on a database that had applied the whole archived chain. On one
that stopped part-way, wrangler would skip the baseline and never run the rest
of the archive, and nothing would say so. `scripts/cire-db-migrate.ts` reads
the target's ledger before anything is applied:

| The ledger holds | Verdict |
| --- | --- |
| nothing, or no `d1_migrations` table | a fresh database — apply |
| `0001_initial.sql` and live migrations, numbered after the archives | built from the baseline — apply |
| `0001_initial.sql` alone | apply if every table and index this baseline creates is stored there as written; otherwise an older baseline built it — **refuse** |
| archived migrations, every one from the start of their chain to the archive's newest | built from an older chain, complete — apply |
| archived migrations with any of that run missing | **refuse**, naming the missing files |
| a name that is not archived yet is numbered within the archive | a migration from outside this chain ran there — **refuse** |
| no `0001_initial.sql` | **refuse** |

The archived migrations are both archives' names, in Wrangler's order. A chain
starts at one of the names in `CHAIN_STARTS` in `scripts/cire-db-migrate.ts`:
`0002`, where the original chain began, `0058`, the first migration after the
first baseline, and `0082`, the first after the second. The ledger read gives
up after two minutes, so a stalled call fails instead of hanging.

A bare `wrangler d1 migrations apply` makes no such check. A refused local
database is rebuilt with `db:reset`, never brought level by applying archived
files by hand.

**Dev and production** are migrated by the cire stack with Alchemy, never by
these scripts, and neither is handed this baseline. Each recorded the long-lived
chain by name and hash, so the stack hands both that chain as written, then
every migration in `migrations/` after the baseline (`CIRE_DB_LONG_LIVED_MIGRATIONS`
and `CIRE_DB_PRODUCTION_MIGRATIONS` in `cire/infra/src/declaration.ts`; the
`longLived` source in `shared/infra/src/migrations.ts`). Production's ledger
also holds every name of the original chain, so the stack hands Alchemy a
placeholder under each (`archivedPlaceholder()`): none ever runs there, and on a
database whose ledger lacked one it fails rather than run archived SQL. Before
anything writes, the release refuses a production ledger missing an archived
file, or one behind a later applied file, as this table would
(`wiki/shared/production-deploy.md` §4.2). An investigation stage gets
`migrations/` alone, and builds from the baseline.

Both archives live outside `migrations_dir`, so Wrangler applies neither. The
tests that replay them to prove what a migration did to existing rows are listed
in `migrations-archive/README.md`. Live migrations after the baseline are
timestamped; every name sorts after both archives' (`scripts/check-migration-orders.ts`
refuses one that does not).

### Squashing the chain

When `scripts/guard-d1-migration-cost.ts --all` nears its line, squash the
chain rather than raise the line. A squash changes nothing dev or production are
handed: the files it moves go into `migrations-archive/long-lived/` under the
names and with the bytes their ledgers recorded, and the stack hands both
databases that chain, so Alchemy finds every recorded name with its recorded
hash and nothing new to apply. So a squash needs no production check and no
release first: a migration production has not applied yet stays a real file in
the long-lived chain, and the next release applies it as it would have.

1. `git mv` every migration in `migrations/` after the baseline into
   `migrations-archive/long-lived/`, under the name it has. The long-lived
   chain's own `0001_initial.sql`, the baseline dev and production recorded,
   never changes; the baseline in `migrations/` is the one that is replaced.
2. Append the first migration you moved to `CHAIN_STARTS` in
   `scripts/cire-db-migrate.ts`: a local database built from the baseline you
   are replacing holds that name first.
3. `bun run scripts/cire-db-baseline.ts` writes the new `migrations/0001_initial.sql`
   from a replay of the long-lived chain. Never edit it by hand.
4. Update the counts `ddl-lockstep.test.ts` and `scripts/tests/cire-db-migrate.test.ts`
   assert of the long-lived chain, if they no longer hold.
5. Run `bun run --cwd cire/api test`, `bun run --cwd cire/api test:d1`,
   `bun run test:scripts`, and `bun run --cwd shared/infra test:d1`, whose
   squash cases (S1 to S6 in `tests/d1/ledger-conversion.test.ts`) prove on a
   local D1 that production and dev take the release with no write and a new
   database builds the whole schema in one migration.
6. Read the new cost from the guard. The line in
   `scripts/d1-migration-cost-budgets.txt` is the owner's to set, and only ever
   moves down at a squash; update the figures in `migrations-archive/README.md`,
   this file, `wiki/conventions/bundle-size-guards.md` and
   `wiki/shared/free-tier-limits.md`.
7. The pull request needs the `migrations:rewrite` label, or the migration
   history guard refuses the moves and the new baseline.

What a squash costs elsewhere:

- **An investigation stage built before it** is refused by Alchemy before
  anything writes: its ledger names files `migrations/` no longer holds. Its
  database is retained when the stage is destroyed, and a redeploy finds it by
  name, so delete `cire-db-<stage>` in the dev Cloudflare account, then deploy
  the stage again.
- **A local database that lags the long-lived chain** is refused by `db:push`;
  rebuild it with `db:reset`.
- **Rebuilding `cire-db-dev` from nothing** replays the whole long-lived chain
  (200 schema writes now, more after each squash), which the cost guard does not
  price. No job does that.

### How a migration is made

A migration is one file, `migrations/<YYYYMMDDHHMMSS>_<name>.sql`, stamped in
UTC, and nothing else is committed with it: no journal, no snapshot. Two
branches that each add one touch no file in common, so neither blocks the
other. Wrangler applies the files in `migrations/` by leading number, then
name, so a timestamped file sorts after every numbered one, and it records each
by name in D1's `d1_migrations` table.

`db:generate` (`scripts/db-generate.ts`) has drizzle-kit write the SQL. It
snapshots `schema.ts` as it stands at `HEAD` (or `--from <rev>`) in a temporary
directory and diffs the working tree against that one snapshot. So:

- **Commit one migration with its schema change before generating the next.**
  It refuses while a `.sql` in `migrations/` is uncommitted, and refuses an
  empty diff: if the schema change is already committed, pass
  `--from <the commit before it>`.
- **A rename is never guessed.** On a terminal drizzle-kit asks; elsewhere it
  exits 2 and prints the `--hints` JSON to pass back.
- **A data-only or hand-written migration** is `--custom`: an empty file to
  fill in. It must hold a statement before it merges.
- **A copy-and-swap table rebuild is refused**: D1 enforces foreign keys, so
  dropping a parent table cascades into its children
  (`wiki/cire/cire-development.md` §Adding a column). A table nothing cascades
  from may be rebuilt by hand with `--custom`, under the `migrations:rewrite`
  label; `migrations-archive/long-lived/20261026040620_seating_plans.sql`
  rebuilds `seating_assignments` so.
- It writes a text primary key `NOT NULL` and a boolean default as `1` or `0`,
  as the deployed chain does.

Never run `drizzle-kit generate` or `drizzle-kit up` here directly. The first
writes a folder and a `meta/` journal wrangler never applies; the second
renames existing migrations, and a renamed file is applied again on every
deployed database.

What proves a migration right, in CI:

| Check | What it refuses |
| --- | --- |
| `cire/api/tests/db/ddl-lockstep.test.ts` | a chain that does not build what `schema.ts` and `setup.ts` declare, or anything in `migrations/` that is not a flat `.sql` with a statement |
| `scripts/check-migration-orders.ts` | new files that fail, or leave a different schema, when applied in name order (a fresh or production build) and after the base chain (the dev tier); new files that sort before a file already on the base or in the long-lived chain |
| `scripts/guard-migration-history.ts` | an edited, deleted or renamed migration, a badly named or empty new one, a copy-and-swap rebuild — the `migrations:rewrite` label lifts all but the empty-file rule |

**Refresh local data after pulling**

```bash
bun run db:reset
```

## Seed contents

The canonical seed data lives in **`seed/data/`** (`events.ts`, `guests.ts`, `wedding.ts`) — a single source of truth consumed two ways:

- `cire/api/src/db/setup.ts#seedDb` imports it (via `@cire/db/seed`) for the in-memory test seed.
- `seed/generate.ts` **derives** `seed/dev-seed.sql` from it (the local-D1 seed). The SQL is a generated file — never hand-edit it. Run `bun run --cwd cire/db seed:generate` after changing anything under `seed/data/`. `seed.test.ts` fails CI if the committed SQL drifts.

This replaced the old hand-mirrored pair (`apps/api/src/data/{events,guests}.json` + a separate hand-written `dev-seed.sql`), which could silently drift.

Seeded shape:

- **5 events** (Catholic / Kitchen Tea / Mehendi / Hindu / Reception, Oct–Nov 2026, Sydney)
- **4 families** with stable UUIDs:
  - `TESTONE-IVY-AA11` — Ada (Testfamily)
  - `TESTTWO-OAK-BB22` — Bo, Cleo, Dot (Sampleton)
  - `TESTTRE-DEW-CC33` — Nori (Exampleton)
  - `TESTFOR-JOY-DD44` — Eli (Placeholder)
- **6 guests** + **15 invitation links** (per-event-per-guest)
- **A seating chart** on the Reception, in one plan, "Plan 1": 2 tables, Ada,
  Bo and Eli seated, Cleo not

Use `TESTFOR-JOY-DD44` as the dev claim code (Eli is invited to every event).

## Conventions

- Every schema change touches **three surfaces together**: the migration SQL,
  `src/schema.ts`, and the `DDL` string in `cire/api/src/db/setup.ts` —
  `cire/api/tests/db/ddl-lockstep.test.ts` diffs all three and fails on drift.
- D1 migrations are **forward-only**. No `DOWN` blocks. To retire a column, stop using it in one release and `ALTER TABLE … DROP COLUMN` in a later one (`wiki/cire/cire-development.md` §Adding a column).
- After editing `schema.ts` AND any wrangler binding, regenerate types: `bunx wrangler --config cire/api/wrangler.toml types`.
- The dev seed reaches the local D1 and the dev tier's (through the cire stack), never production. Production data flows in via the organiser spreadsheet import (`/api/organiser/import/{preview,apply}`).
