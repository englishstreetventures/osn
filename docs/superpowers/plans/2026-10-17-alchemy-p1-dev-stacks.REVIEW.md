# Stress test of the P1 dev-stacks plan

Plan: `docs/superpowers/plans/2026-10-17-alchemy-p1-dev-stacks.md`. Attacker run 1, 2026-10-17, read-only, a fresh context. Each finding is listed with what was done about it: fixed in the plan, rejected (with the fact it got wrong), or escalated to the owner.

## Run 1 — 23 findings

| # | Severity | Finding (short) | Outcome |
|---|---|---|---|
| 1 | blocker | Verify jobs with no `if:` are skipped when an upstream stack job (musubi) was skipped, because the implicit `success()` covers every upstream job | **Fixed.** Stacks no longer need each other (finding 11's fix). The per-surface jobs carry an explicit `if: ${{ !cancelled() && needs.<stack>.outputs.deployed == 'true' && needs.<stack>.outputs.<surface>_healthy == 'true' }}` (Task 11). |
| 2 | blocker | After a smoke-check rollback, Alchemy's state still holds the broken version, so the next run plans a noop, checks the old version and records success at a commit containing the broken code | **Fixed.** The rollback marks its deployment with a `workers/message` annotation that starts `Smoke check failed`. The next stack run's snapshot finds any Worker whose newest deployment carries that mark and deploys with `--force`, re-uploading what the commit declares. The smoke check fails an `unchanged` Worker whose newest deployment carries the mark, so a failed heal can never record success (Decision 3, Tasks 10–11). |
| 3 | blocker | The `smoke_fail: osn_api` dispatch after a no-change deploy deploys nothing, so it can never roll back | **Fixed.** New dispatch input `force` (Alchemy `--force`: every noop resource becomes an update, `ALC/Plan.ts:1619-1624`). Proof order: deploy; `expect_no_change`; `force` with `smoke_fail: osn_api` (rolls back, red); a plain dispatch (self-heals through finding 2's force, green). The issue's Done-when is edited to match. |
| 4 | major | A verify job's rollback can overwrite the next run's newer deploy (no shared concurrency) | **Fixed.** The smoke checks and rollbacks run as steps of the stack job, inside its `deploy-dev-<stack>` group, as today's dev jobs run them inside theirs. The per-surface jobs only carry the Deployment record (Decision 2, Task 11). |
| 5 | major | A deploy that fails part-way leaves uploaded versions unchecked and never rolled back; `--expect-no-change` fails only after the deploy applied | **Fixed.** `compare` and the smoke steps run `if: ${{ !cancelled() && steps.snapshot.outcome == 'success' }}`, so a Worker uploaded before a failure is still checked and rolled back. No per-surface record is written when the deploy step failed. `expect_no_change` is documented as a check on the plan line of a deploy that has already applied, which is what the proof needs (Task 11). |
| 6 | major | The guard does not stop a stored-profile fallback: Alchemy needs both `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` to use the environment; Bun loads `.env` files into `process.env` | **Fixed.** `assertDevDeployTarget` requires both, and `refuseDotEnvFiles(cwd)` refuses a stack directory holding `.env`, `.env.local`, `.env.production` or `.env.production.local`; the Facts row is corrected (`ALC/Auth/Resolve.ts:51-90`; `alchemy/bin/cli.js:17`).
